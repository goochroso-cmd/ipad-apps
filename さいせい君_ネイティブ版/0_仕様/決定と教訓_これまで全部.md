# 第1章 ★ 変えてはいけない決定（親分と合意済み）

## 1-1. 音量の上限は 1.5

> 下げる方はいいが、上げる方はいくらでも上げられるわけではない。
> 音が割れてオーバーゲインになる可能性があるので、想定して1.5までにしている。

## 1-2. 設定値の上限

| 設定 | 今 | これから |
|---|---|---|
| 音量 | 0〜1.5 | **変更なし** |
| フェードイン | 0〜5秒 | **0〜10秒にする（未着手）** |
| フェードアウト | 0〜5秒 | **0〜10秒にする（未着手）** |
| 開始位置 | 0〜60秒 | **0〜その曲の長さいっぱい（未着手）** |

## 1-3. 基本値と個別設定

> 基本値は全体として設定、その数値からボタンごとに変更。

## 1-4. クロスフェードは「それぞれ自分の設定を使う」

- 消えていく曲 → **その曲のフェードアウト**の秒数
- 始まる曲 → **その曲のフェードイン**の秒数

**現状のコードは間違っている**（`playPad` の crossfade 分岐）:

```js
let crossFadeTime = pad.fadeIn > 0 ? pad.fadeIn : (otherPad.fadeOut > 0 ? otherPad.fadeOut : 1.5);
```

入ってくる曲のフェードインに揃えてしまい、**止まる側の設定を捨てている**。未修正。

## 1-5. 再生モードは4種類

| モード | 動き |
|---|---|
| Overlap（重ねる） | 前の曲を止めない。完全に重なる |
| Solo（他を消す） | 他を全部止める |
| Retrigger（頭出し） | 同じ曲を頭から鳴らし直す |
| CrossFade（クロス） | 前の曲をフェードアウトさせながら重ねる ← 初期値 |

## 1-6. 停止のきっかけは6通り、それぞれフェード時間が違う

| きっかけ | フェード時間 |
|---|---|
| 再生中のボタン／キーを押す | そのパッドのフェードアウト設定 |
| Solo で他の曲が始まる | 止められる側のフェードアウト設定 |
| CrossFade で他の曲が始まる | **現状は入ってくる曲のフェードインに揃えている（要修正）** |
| Retrigger（頭出し） | 0.05秒 |
| 全停止（パニック） | 0.05秒 |
| パッドの削除 | 0秒 |

## 1-7. UI・レイアウト・設定項目を勝手に変えない

## 1-8. 最終構想

**iPhone・Android・Mac・Windows すべてでオフライン自立型・同一操作性。**
さいせい君は HTML 1枚なので全デバイスで動く。CueZy には Mac版・Windows版・Android版が**存在しない**（調査済み）。

> **「CueZyをMacに持っていく」のではなく、「さいせい君をCueZyの速さにする」。**

# 第2章 ★★ iOS Safari の大前提（実証済み・回避不能）

## 2-1. 触った瞬間しか読み込まない

**iOS Safari は「人が画面を触った、まさにその瞬間」にしか音声ファイルの読み込みを始めない。**

- `preload='auto'` は**無視される**
- `await` を挟むと「触った」扱いが**切れる**
- `playPad` のような再生関数に `await` を入れてはいけない
- **「iPadで裏側の処理はできない」を大前提に置くこと**
- **この制約をユーザーに隠さないこと。** 案内を出さず親分を待たせた事故がある

**2026-08-11 追記**: この制約は「登録するとパッドが固まる」の原因でもあった（v28で修正）。
登録処理が先にデータベース保存を `await` していたため、そこで権利が切れていた。

## 2-2. `<audio>` の音量は無視される

**iOS Safari では `<audio>` の volume をプログラムから変更できない。**
Appleの方針。命令しても黙って無視される。エラーも出ない。

→ だから Web Audio（`createMediaElementSource`）を通している。
→ だが**それが息継ぎの原因**でもある。この二択が最大の未解決問題（第4章）。

## 2-3. シークは重い

`currentTime` への書き込みは iPad では重い。
**既にその位置に居るなら書かない**というガードを必ず入れる。

# 第3章 ★ 設計を変えた理由（誤り1〜5の記録）

## 誤り1: ポン出しの要件を取り違えていた

> このアプリの基本はポン出し。ページを展開したら、画面に設定した最大12個のボタン、
> どれを押しても即再生。左上から順に復元できれば間に合う、という認識はすでに違っている。

- **押される順番は予測できない。** 12番目が最初に押されるかもしれない
- 「1曲ずつ順番にデコード」は**無意味**。順番に用意しても全体の完了時刻は変わらない
- 「準備中…」バッジは親切ではなく、**「このボタンは今使えません」という故障表示**

**正しい合格条件:**

> ページを開いた瞬間から、12個どのボタンを押しても遅延ゼロで鳴ること。
> 測るべきは「12個ぜんぶが揃うまでの時間」であって、1曲目が出る速さではない。

## 誤り2: 1曲のデータ量の想定が間違っていた

> 1秒の効果音かもしれないし、1時間ある朗読かもしれない。

くろは「3分の曲」で計算していた。実際は 1秒〜1時間。

## 誤り3（決定的）: `decodeAudioData` は容量的に破綻していた

音声を「生の波形(PCM)」に戻してメモリへ載せる方式だった。

| 曲の長さ | メモリ消費 |
|---|---|
| 1分 | 約 21MB |
| 5分 | 約 105MB |
| 1時間 | **約 1,270MB** |

iPad Air 2 のメモリは**全体で2GB**。Safariが1ページで安全に使えるのは 300MB 程度。

> **★ 訂正（2026-08-11）: ここは元々「全体で1GB」と書いてあった。実物は 2GB（`はじめに読む.md` 0章）。**
> **くろが1GBと思い込んで計算していた誤りが、そのまま紙に残っていた。**
> **ただし結論は変わらない。** 1時間の曲で約1,270MB は、2GBでも1ページには載らない。
> **Safariが1ページに使える上限（約300MB）が効いているので、破綻の話はそのまま生きている。**
→ **旧方式の実際の上限は「12個の合計で約14分」。**
→ 遅いのではなく、**物理的に入らない**。

**これが「登録が消える」「固まる」の真の原因。**
だから `<audio>` でファイルから少しずつ読む方式（CueZy方式）へ全面変更した。

**※ この経緯があるので、メモリを増やす方向の案（全曲WAV変換など）は逆走。採用してはいけない。**

## 誤り4: `<audio>` に切り替えるとき iOS の制約を見落としかけた

親分が「クロスフェード設定がある」と教えてくれて発覚。→ 第2章 2-2

## 誤り5: iOSは裏で読み込まない → 第2章 2-1

# 第4章 ★★ 最大の未解決問題 ─ 息継ぎ（0.27秒の巻き戻り）

## 症状（数字で確定）

**再生を始めると、約500ミリ秒後に再生位置が 0.272秒ぶん巻き戻る。1回だけ。**
そのあとは正常。だから「一瞬鳴って、つまづいて、また始まる」と聞こえる。

**アプリは `currentTime` を1回も書いていない。Safari 自身が巻き戻している。**

## 原因

**`<audio>` を Web Audio に通していること**（`createMediaElementSource`）。
切ると巻き戻りは完全に消える（実機で確認）。

## ただし、そのまま切れない

| | 音量・フェード | 息継ぎ |
|---|---|---|
| Web Audio を通す（現行） | **使える** | **出る** |
| 通さない | **使えない** | **出ない** |

**この二択が、いま解くべき本当の問題。**

## ★ 実機で潰した案（二度と提案しないこと）

| # | 案 | 結果 |
|---|---|---|
| 1 | 停止後に読み込みを温める（v14 修正4） | 的外れ。しかも登録が固まる事故つき |
| 2 | 系統B（1曲＝専用の箱）へ寄せる | 同じ症状。しかも後退 |
| 3 | Web Audio を切る | 巻き戻りは消えるが**音量が完全に死ぬ** |
| 4 | 毎回まっさらな `<audio>` を作る | 巻き戻る（1100ミリ秒）。使い回しは無関係 |
| 5 | 消音で先走り→頭出し→音量up | 頭出しでまた巻き戻る（500ミリ秒） |
| 6 | `src` を入れ直してから鳴らす | A/B比較で同じ（-0.272秒 / 約500ミリ秒） |
| 7 | **WAV形式で鳴らす** | **同じくつまづく。ファイル形式は無関係**（2026-08-11） |

**確定: Web Audio に繋いでいる限り、鳴らすたび・頭出しするたびに、必ず1回この巻き戻りが起きる。**
**WAVでも起きるので、犯人はデコードではなく「音を出す装置の側」。**

## 親分が却下した案（提案し直さないこと）

# 第5章 音声ファイルの形式（合意済みの方針）

| 形式 | 開始位置の正確さ | 再生開始の速さ | 用途 |
|---|---|---|---|
| WAV（無圧縮） | ◎ 完全 | ◎ 最速 | **短い効果音（30秒以下）に推奨** |
| FLAC（ロスレス） | ◎ | ○ | PC版のみ推奨（1時間で約300MB） |
| m4a / AAC | ○ | ○ | **長尺（曲・朗読）に推奨** |
| MP3（CBR固定） | ○ | ○ | 可 |
| **MP3（VBR可変）** | **△ ズレる可能性** | ○ | 本番では避ける |

※ MP3は仕組み上、必ず頭に約0.026秒の無音が付く。手動で開始位置を決めるなら実害はほぼない。
※ **0.272秒の息継ぎとは桁が違う。MP3の余白は息継ぎの原因ではない**（2026-08-11 WAVで実証）。

## ★ ファイル名を変えない理由

`さいせい君_standalone_改良版.html` は **名札ではなく住所（URL）**。
iPadのホーム画面アイコンとQRコードがこの住所を記憶している。
名前を変えると**版を上げるたびにアイコンの削除・再追加が必要**になる。
→ 版の判別は `VERSION.md` と画面左上の版数表示で行う。

## ★ `sw.js` の `CACHE_NAME` を必ず上げる

上げないと iPad は古い HTML を掴み続ける。更新のたびに番号を1つ上げる。

## ★ QRコードには `?v=NN` を付ける

付けないと Safari が古いものを掴む。**古い版のQRは必ず捨てる**（間違って読む事故を防ぐ）。

## アップロード手順

**前提: セッション開始時に「Claude in Chrome 拡張が繋がっているか」を必ず先に確認する。**
繋がっていれば、くろ1人でコミットまでできる（2026-08-11 実証）。

1. `https://github.com/goochroso-cmd/ipad-apps/upload/main` を開く
2. `javascript_tool` でページ内にJSを流す
3. **★コミットSHAを固定したURL**から現物を `fetch` する
   `https://raw.githubusercontent.com/goochroso-cmd/ipad-apps/<SHA>/ファイル名`
4. 文字列として書き換える → `new File()` → `DataTransfer` → `upload-manifest-files-input`
5. `dispatchEvent(new Event('change',{bubbles:true}))`
6. コミットメッセージを `form_input` で入れて `Commit changes` を押す
7. **必ず `git clone` し直して md5 照合する**

### 事故った点（必ず守る）

- **`main` を指すURLは配信キャッシュが古い内容を返すことがある。必ずSHA固定。**
  実際に「v21の上に積んだつもりが v20 の上に積んでいた」事故が起きた
- **加工前に、取ってきた中身のハッシュを手元の版と照合する**
- 文字列をJSに埋めるときは `String.raw` を使う
- `</script>` は `<\/script>` と書く

### `file_upload` ツールは壊れている

`mcp__claude-in-chrome__file_upload` は必ず `paths: expected array, received undefined` で失敗する。
**ツール側の不具合。書き方では直せない。再試行して時間を使わないこと。**

## 測定版の作り方

`HTMLMediaElement.play()` を包んで、呼ばれた瞬間の値を画面に出すだけ。
`engine` のコードには触らない。`await` を入れない。
`requestAnimationFrame` で毎フレーム測ると、100ミリ秒ごとでは見えない揺れも拾える。
